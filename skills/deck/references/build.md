# Build

Used in step 7.

## Choosing how to build

- Look at what this session can actually do to make slides: slide-deck artifact types, skills that build presentation files, connectors to apps that make presentations, code that writes a file, and whether you can see the rendered result. Offer only what exists. Facts about a tool (features, limits, syntax) come from its current documentation, not from memory.
- Judge each option against this deck: the guide or a mandatory template, how the deck will be shared (a link, a file, a PDF), who edits it afterwards and where, and whether you can review it rendered.
- Offer up to four options, numbered, each with one pro and one con for this deck, and recommend one with the reason. One option always exists: the approved plan as a specification the user builds from by hand or pastes into another tool, with a warning that external tools often alter the data.
- If the chosen option needs a file the user hasn't given (a template), ask for it before building.

## Building

The two gates are the specification: the approved slide text with the Gate 2 changes, the concept and the illustration plan. No rewritten titles, added slides, swapped forms or text the plan doesn't have, such as speaker notes; if the tool can't do something the plan asks, ask before adapting it.

## Reviewing the rendered deck

Look at images or a preview of the slides, not only the code or text behind them, and fix before handing it over:
- **Against the plan:** every slide present, the exact text, correct data, the planned form and highlight.
- **Form:** text cut off, overflowing or overlapping; type too small for the format; weak contrast; a color meaning two things.
- **The concept** holds across the deck.

Fix what is only form; anything that changes content is a proposal. Tell the user what you fixed. If you can't see the rendered result (a specification for another tool, a file the session can't render), hand this review over as a checklist for the user.

## After the user sees it

The user judges the deck. Apply their fixes in the built deck, slide by slide, instead of rebuilding it, so what was already right stays as it is. A fix that changes an approved decision (the concept, the arc, a slide's point) is named as one before it is applied.
