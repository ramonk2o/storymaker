# Handoff

Used to choose how the deck is built (step 2.1, or the build line of the express proposal), to build and to review the result (Phase 3).

## Choosing how to build

1. **Look at what this session can do right now** to produce slides: slide-deck artifact types, skills that build presentation files, connectors to apps that create presentations, and whether you can view the rendered result. Offer only what is actually available; never assume a tool exists. If the session can search for skills or connectors that aren't installed, you may mention one that would clearly help, in one line.
2. **Judge each option against this deck:** a mandatory template or brand identity; who edits the deck afterwards, and where; how it will be shared (a link, a file, a PDF); whether it needs speaker notes; what the visual concept demands (charts, custom layouts); and whether you can review the rendered slides, which the review below depends on. If the account has a design system and an option can apply it, say so.
3. **Present two to four viable options,** numbered, each with one pro and one con for this deck, and recommend one with the reason. In express mode, one line per option. Mention in one line the two fallbacks that always exist:
   - **Prompt for an external slide tool:** a complete, self-contained prompt built from the Production plan — context, audience, global rules and, slide by slide, title, visual, data and text. Warn that chart data must be checked afterwards, because external tools often alter it.
   - **Build checklist:** the Production plan as a slide-by-slide checklist for the user to assemble by hand.

If the chosen option needs a file (a template), ask for it before building. If it is no longer available when the build starts (for example, in a new conversation), say so and choose again.

## Building
- The Production plan is the specification: no rewritten titles, added slides, swapped visuals or invented data. If something isn't possible in the chosen tool, ask before adapting.
- Pass everything decided to the build: global rules, identity, each slide's content and the speaker notes.

## Review on the rendered deck
Look at images or a preview of the slides, not only the code or text behind them. Check, most serious first:

- **Against the plan:** every slide present, exact titles, correct data, highlight on the figure the title claims, speaker notes in place.
- **Glance test:** each slide's point readable in about three seconds; one point per slide.
- **Proof:** each visual proves its title; nothing decorative or merely interesting that doesn't serve it.
- **Rhythm:** no more than three dense slides in a row; the hook, the memorable moment and the close stand out from the slides around them.
- **Form:** text cut off, overflowing or overlapping; a title past two lines; type too small for the format; weak contrast; a chart missing source and period; the same color meaning different things.
- **Concept:** the visual concept holds across the deck; layouts vary by the slide's job instead of repeating one stock layout everywhere.

Fix what is only appearance; for anything that changes content, ask first and write it back into the gate documents. Tell the user what was fixed and what still diverges from the plan.

If the chosen option doesn't let you see the result (a prompt for an external tool, a build checklist), deliver this review as a checklist for the user to run after assembling.
